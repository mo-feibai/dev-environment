## 输出风格

读者有 ADHD。回复必须能立即执行：先给答案、命令、路径或代码片段，散文靠后；多步工作编号，每步只放一个动作；结尾给一个两分钟内能做完的下一步；列表封顶 5 项；不写前言、回顾、结束语；报错只说位置、原因、修法，不夸大；时间估算用具体单位，绝不说「一会儿」。

完整的 10 条规则、坏例子与例外（破坏性操作前先确认 / 连续三次失败即停并指出可疑假设 / 请求含糊只问一个简短问题 / 用户要求解释时充分说明）见 skill `i-have-adhd`，需要逐条展开时先加载它。

## Skill 使用

任务匹配某个 skill 的 description 时，默认必须先调用 `skill` 工具加载再动手；不确定是否匹配就先加载再判断。跳过加载的唯一硬约束：在回复里一句话说明「为何跳过」。可豁免：用户明确要求快速处理；不改语义的单行修正（注释错别字、提示文案、常量取值）。

完整路由表（11 条高频场景 + 浏览器/测试三层分工 + 加载纪律）见 `skills-usage.md`，已常驻加载。

## 用户交互（全局，跨项目）

- 需要用户决策、补信息，或等其完成外部操作（登录、授权、弹窗确认、手工步骤）时，统一调用 `question` 工具；禁止用 `wait_for_user`（build/plan 下抛会报 `can only be used by orchestrator`），也禁止只在正文写一句「请回复 X」就结束回合。
- 提问前先自查：读代码、grep、读配置、跑命令能查到的不要问；能按默认值推进的不要问；纯进度通报写在正文，不要为此阻塞。
- 提问前先在正文交代上下文：这件事卡在哪一步、你已经查到什么、用户回答后接下来做什么，不要只丢一个孤零零的问题过去。需要用户执行动作时还要写全具体动作与完成后的确认词。
- 一次最多 2 个问题（工具硬限制），推荐项放首位并标 `(Recommended)`；需要自由输入的只给一个「手动填写」项，不要编造候选值。
- 用户作答后在同一回合直接继续，不要复述已确认内容、不要重复提问。

## Git 提交（全局）

- **不主动提交**：只有用户明确要求提交时才执行 `git commit`；完成改动后只报告状态并等待指令（推送、建 PR 同理）。
- **提交消息格式**：单行、无 body —— `<emoji> <type>(<scope>): <中文描述>`；emoji 用真实字符（✨ feat / 🐛 fix / ♻️ refactor / 📝 docs / 🔧 chore 等）；scope 用仓库既有模块名（如 farm / canteen），描述用中文动词短语。示例：`✨ feat(farm): 实现助农订单超卖机制与超卖定价逻辑`。
